# Food Rush
#### Video Demo:  <URL [HERE](https://youtu.be/4D1LGGZgJEU)>
#### Description:

This project is going to be a small arcade game using lua as a coding language as per the project requirements. The goal of the game is to score as many points as possible, with every 20 seconds the game will get faster and harder to keep up with. There are three different food types that fall from the sky, each with their own speeds, point values, and spawn rates. I added music and sound effects and structured the code based on what I learned from Harvard's CD50 programming course.

To begin, we can start with the main.lua file. This is the file I used to initialize a lot of the important global variables. Things such as the window screen size and the virtual screen size. I imported push.lua and class.lua from CD50 to help me with this project and used it liberally. In love.load I set up random seeds, music, state machines and input tables. One thing of note in this portion is the spawner logic. Separating burger, sushi, and cake spawners (and later a lot of other things) in the main.lua file was necessary since they needed to be global variables that needed to be set after math.randomseed(os.time()) and initialized everytime the game began. Every other "object specific" logic will be implemented into their own .lua files.

Next we can go to the StateMachine.lua. It mostly handles the logic of swapping states and updating every state. BaseState.lua is a "parent" class. It outlines a commonality between "states" that are all inherent from the BaseState.lua, containing init, enter and exit, update, and render functions. Next, we have CountdownState.lua. This state renders numbers on the screen that count down from 3 to 1 before changing states again to the PlayState. It also contains logic to stop the end music if they hit enter before the music ends. Next, we can look at the ScoreState.lua. This .lua file mostly takes in the score that was tracked in PlayState.lua and renders it on the screen. It also starts and stops the main game music. Next, we have the TitleScreenState.lua. This renders text on the screen that says "Food Rush!" and checks if enter is pressed so that it can call StateMachine.lua to swap the state to CountdownState.lua.

Now this is the good part. For PlayState.lua, 90% of the actual game logic is in this lua file. I will go through this file in more detail than the other files. First, we make sure we establish that PlayState is a child of BaseState, which is indicated on line one. Next, we establish global variables such as EATER_SPEED and GRAVITY_INCREASE. The eater speed is set to an arbitrary speed that I thought felt good to control. The gravity increase is meant to be a noticeable change every 10 seconds, but not so much where it would be impossible really fast. We have the init function which initializes Eater() where our eater logic lies, a self.foods table to store all the food we spawned and keep track of them as well as a self.score function to keep track of the overall score that the player gained. Next we have the enter() function, which plays when we enter a state, as defined in StateMachine.lua. In PlayState, it plays a short "start" sound, sets GAME_OVER to false, creates an ELAPSED_TIME variable, and a THRESHOLD variable as well.

PlayState:update(dt) takes in delta time and immediately begins incrementing ELAPSED_TIME. I put this in PlaySate instead of elsewhere like main.lua because I wanted to specifically track the playtime of when the game started instead of also including all the time a player may or may not be in the main menu. While writing this, I also understand that I could keep track of the time by using love.timer.getTime() and getting it again whenever I need it and subtracting by the first time I did it. The reason I did it this way instead is because I believe it would be easier since whenever I hit thresholds, I would need to check the current time to see if it passes it or not, which would be a lot easier this way rather than rechecking the time each time. I also would be displaying that elapsed time on screen, so keeping a counter instead of doing arithmetic each time would overall be easier as well.

This section is the part that took me the most time out of everything. I wanted to do best practices and keep the game scalable in case I ever wanted to add more foods. So the main problem I was facing was trying to keep the logic for each food within its own separate files. Things like art, point values, and fall speeds. The big concern in question here was the spawn rates. I had set a timer for each separate food that triggered that is stored IN the food files themselves. The problem is I needed that information to determine whether or not I wanted to spawn the food in the first place. So keeping those variables as local variables would require the food itself to already be spawned, or at least from what I understand. This would mean I needed it to be global anyway, which would also mean I would've needed to hard code the check for each of those individual checks and timer resets. Also, if I ever wanted to add any other foods or anything else, I would need to hard code that in as well.

I mostly fixed this by keeping the variables global, but doing the main logic in the food lua files instead, using all the global variables. In order to do this, I needed to have functions in the food.lua files that used ONLY global variables. I also needed to create another list of food classes called FOOD_TYPES. This stores the classes instead of every instance of that food that I iterated through to call each of the functions in the food files. This way, if I wanted to add any other spawnable items, I can just add them to this list instead of hard coding each in the PlayState:update(dt) function. Unfortunately, the food spawner times had to be shoved in the main.lua file because the global function of FOOD_SPAWNER was getting initialized before the math.randomseed(os.time()) was. So if I wanted to add anything else, I would also have to make sure they get randomized correctly.

The rest of the update function is rather simple and straightforward. I have a for loop that calls the update function on every food in the self.foods list, a for loop that calls the eats function on eater.lua to check if it ate anything in the self.foods list and adds points before removing that item from the table, an if function that checks if ELAPSED_TIME exceeds or equals the THRESHOLD initialized in PlayState:enter() before calling the gravity increase function and increasing the threshold by 10, and lastly checking if the game is over before removing all entries in the self.foods list and changing the state to score, passing in the self.score variable

The gravityIncrease() function goes through every food class and calls a function of the same name in every food file, which adds GRAVITY_INCREASE to their respective gravity variable. I do it based on class rather than instance so that the foods can be affected even if they haven't been spawned in yet or not. Next, we have the render function, which simply renders self.eater and every food in the self.foods list. It also renders the score and the time, using the ELAPSED_TIME variable. Finally, the exit function simply sets the GAME_OVER variable to true in case it is ever set to false before exiting the PlayState.

Moving on to all the food files, I created a BaseFood.lua file similar to the BaseState.lua file. It contains init, enter, exit, update, resetTimer, gravityIncrease, spawn, getPoints, and render. I put these in this file since every single food will need these functions. As for the individual food functions, I'll go through them once as a unit since it's mostly the same code. We start with setting the class to the food class I had made. We also set the food to be the picture we chose for the food. Then we set all the global variables I was struggling with earlier. The init function sets the size of the food and creates a spawn point. It randomizes self.x and spawns the food just above the screen. The update function applies gravity and then checks if it passes the bottom of the screen. If it does, it sets the GAME_OVER function to true which in the main would cause the game to end. The gravity increase function just adds the global gravity increase variable to the food's gravity. Spawn sets a timer and increments it and when it reaches a randomized threshold defined in main.load, it sets the spawnable variable to true, then randomizes the spawner time again. It then returns if the food can be spawned or not. Reset timer just sets the food timer to 0, and get points just returns the points for the food. This particular function is necessary since each food has their own separate global points variable, it's easier for each class to return their own global variable rather than call each of them manually. The last function renders the food on screen.

The last file we will go through is the eater.lua file. The init function sets the size based on the eater image, the spawn location (which is just the center of the screen and close to the ground) and its movement speed. The update function checks if the player is pressing a or d and setting the eater to that speed or 0 if nothing is being pressed. The eats function calls in foods from the self.food list in PlayState.lua and checks if that food is in the mouth of the eater. Then, render simply renders the eater every frame.
